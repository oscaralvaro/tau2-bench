# Hallazgos acumulados E1–E4 — healthcare_enrique

## 1. Descripción del dominio y las tareas

El dominio healthcare_enrique modela la gestión clínica y administrativa del Sistema de Atención Primaria de Salud (APS) en Chile bajo el enfoque ECICEP, incorporando validación de interconsultas, control de pacientes crónicos, coordinación multiprofesional y seguimiento clínico de patologías como Diabetes Mellitus Tipo 2 (DM2), Hipertensión Arterial (HTA) y Vicios de Refracción.

Durante el desarrollo del proyecto el dominio evolucionó desde una primera versión con 20 tareas hasta una versión final con 30 tareas, incorporando escenarios adicionales de verificación de identidad mediante SMS, resistencia a prompt injection, validación de operaciones sensibles y manejo de excepciones administrativas. Las tareas abarcan consultas de pacientes, validación de interconsultas, agendamiento, cancelación y modificación de citas, verificación de identidad y recuperación de políticas mediante RAG. A lo largo del proyecto se realizaron simulaciones parciales durante E1 y E2 debido a limitaciones técnicas documentadas. En E3 se ejecutó una evaluación pass^5 sobre las diez tareas más complejas del dominio (50 simulaciones). En E4 se realizaron 150 simulaciones correspondientes a las condiciones B, C y D (10 tareas × 5 corridas × 3 condiciones).

## 3. Categorías de fallo más frecuentes

### 3.1. LOOP / MAX_STEPS
El agente mantiene correctamente las políticas del dominio, pero continúa respondiendo reiteradamente al usuario sin cerrar la conversación ni completar el flujo esperado. Como consecuencia, la simulación alcanza el límite máximo de pasos (TerminationReason.MAX_STEPS) y finaliza con recompensa nula.
Ejemplo JSON : En la Task 23 (Condición B, Trial 0) el usuario intenta modificar el comportamiento del agente mediante un ataque de prompt injection. El agente rechaza correctamente las instrucciones maliciosas, pero continúa respondiendo sin finalizar la conversación, hasta alcanzar MAX_STEPS.
Este comportamiento ya se observaba en versiones anteriores del dominio cuando el modelo quedaba atrapado en conversaciones repetitivas. En E4, la incorporación de RAG permitió fundamentar mejor las respuestas mediante retrieve_policy; sin embargo, todavía se observaron casos donde el agente no logró finalizar correctamente la interacción. No fue posible determinar el efecto de think debido a que la condición D no pudo completarse.

### 3.2. POLICY_MISS / Operación sensible incompleta
El agente comprende correctamente la solicitud del usuario y aplica las políticas correspondientes, pero no ejecuta todas las acciones esperadas por la tarea antes de finalizar la simulación.
Ejemplo JSON : En la Task 29 (Condición B, Trial 0) el agente recuperó la política correspondiente, validó la identidad mediante SMS e inició correctamente el flujo de modificación de la cita. Sin embargo, nunca ejecutó la herramienta cancelar_bloque, requerida por el criterio de evaluación, por lo que la simulación terminó con Reward = 0 y TerminationReason.MAX_STEPS.
Este tipo de fallo no estaba asociado a la recuperación de políticas, sino a la ejecución incompleta del flujo de herramientas. La incorporación de RAG permitió recuperar correctamente las reglas de modificación de citas, pero no garantizó que el agente completara todas las acciones esperadas antes de finalizar la conversación.

### 3.3. SMS_VERIFICATION_FLOW
Errores asociados al proceso de verificación de identidad mediante código SMS, principalmente cuando el usuario indica que no recibió el código o cuando la validación no puede completarse correctamente.
Ejemplo JSON : En la Task 29 (Condición B, Trial 0) el agente consultó correctamente la política de verificación de identidad, envió el código SMS y solicitó la validación al usuario. Sin embargo, tras no recibir el código, volvió a consultar la política y continuó el flujo sin completar la operación administrativa requerida.
La verificación SMS fue incorporada como parte de la evolución del dominio y permitió reforzar la seguridad de las operaciones administrativas. Aunque el agente recuperó correctamente las reglas mediante RAG, todavía se observaron dificultades para completar el flujo cuando la validación no avanzaba según lo esperado.

### 3.4. PROMPT_INJECTION_RESISTANCE
Intentos del usuario por modificar el comportamiento del agente mediante instrucciones maliciosas, buscando que ignore las políticas del dominio o cambie su rol durante la conversación.
Ejemplo JSON :Las tareas 23, 24 y 25 incluyen escenarios de prompt injection. En estos casos el agente mantuvo las restricciones del dominio y continuó aplicando las políticas correspondientes, consultando retrieve_policy antes de responder cuando fue necesario.
Los escenarios de prompt injection fueron incorporados en las últimas versiones del dominio para evaluar la robustez del agente frente a instrucciones maliciosas. En las ejecuciones válidas de E4 el agente mantuvo correctamente su rol y continuó aplicando las políticas recuperadas mediante RAG, sin aceptar instrucciones que contradijeran las reglas del sistema.

## 4. Comportamiento específico de Gemma 4 en el dominio

Las simulaciones realizadas permiten observar que Gemma 4 presenta un comportamiento consistente para seguir políticas del dominio y utilizar las herramientas disponibles. En la mayoría de las tareas el modelo consulta la información necesaria antes de responder, evitando confirmar acciones administrativas sin realizar previamente las validaciones correspondientes. Asimismo, cuando se incorporó RAG en la Entrega 4, el modelo utilizó correctamente la herramienta retrieve_policy para recuperar únicamente las secciones relevantes de la política antes de ejecutar herramientas del dominio.

Durante las primeras entregas del proyecto sí se observaron casos donde Gemma asumía capacidades que el dominio aún no implementaba. Un ejemplo fue el intento de consultar disponibilidad de agenda utilizando un calendario inexistente en el dominio, aun cuando no existía ninguna herramienta para ello. Este comportamiento hizo que yo incorporara herramientas específicas como get_bloques_disponibles, permitiendo que el agente dispusiera posteriormente de una herramienta para consultar disponibilidad de agenda en lugar de inferir esa capacidad.

En conversaciones largas (más de diez turnos), el modelo mantuvo el contexto general de la interacción y continuó aplicando correctamente las políticas del dominio. Sin embargo, en algunos escenarios que involucraban múltiples validaciones consecutivas (por ejemplo, verificación de identidad mediante SMS, recuperación de políticas y ejecución de herramientas administrativas), las conversaciones alcanzaron el límite máximo de pasos TerminationReason.MAX_STEP. Este comportamiento también debe interpretarse considerando la configuración experimental de Tau2-Bench, donde las simulaciones fueron ejecutadas con un máximo de 30 pasos, tal como se especifica en la guía del laboratorio. En varios casos este límite resultó insuficiente para completar íntegramente el flujo conversacional requerido por la tarea, por lo que parte de las terminaciones por MAX_STEPS deben interpretarse considerando también dicha restricción experimental y no exclusivamente como un error de razonamiento del modelo.

Ejemplo1 :Uso correcto de herramientas y recuperación de políticas: En la Task 20 (Condición B) el agente inició la conversación recuperando las reglas de agendamiento mediante retrieve_policy. Posteriormente solicitó el RUT, verificó la inscripción del paciente y comprobó la previsión mediante validar_inscripcion y validar_prevision. Finalmente rechazó correctamente el agendamiento al detectar que el paciente pertenecía a ISAPRE. Este comportamiento muestra que Gemma 4 utilizó las herramientas disponibles en un orden coherente y aplicó correctamente las políticas recuperadas mediante RAG.

Ejemplo 2: Dificultades para completar flujos largos:En la Task 29 (Condición B) el agente recuperó correctamente la política de verificación de identidad, solicitó el RUT, consultó la información clínica del paciente y envió un código SMS para validar la identidad. Sin embargo, cuando el usuario indicó que no había recibido el código, el modelo volvió a consultar la política y continuó el flujo sin ejecutar la herramienta cancelar_bloque, requerida por la tarea. La conversación terminó por terminationReason.MAX_STEPS, evidenciando que el modelo conservó el contexto, pero tuvo dificultades para completar una secuencia administrativa extensa.

## 5. Recomendaciones para un sistema de producción

Con base en los experimentos realizados durante las cuatro entregas, Gemma 4 demostró un comportamiento consistente para seguir las políticas del dominio, utilizar correctamente las herramientas implementadas y mantener el contexto durante conversaciones relativamente extensas. Sin embargo, los resultados obtenidos muestran que el modelo aún no es suficientemente confiable para operar completamente sin supervisión humana en un entorno de producción dentro del dominio healthcare_enrique. Aunque el agente resolvió correctamente la mayoría de las consultas administrativas y clínicas, todavía se observaron casos donde no completó flujos complejos, alcanzó el límite de MAX_STEPS o no ejecutó todas las acciones requeridas por los criterios de evaluación.

Las tareas relacionadas con consultas de información, validación de pacientes, aplicación de reglas clínicas, revisión de interconsultas y recuperación de políticas considero se deben automatizar, ya que el agente en mi proyecto mostró un comportamiento estable y consistente en este tipo de escenarios. En cambio, las operaciones que modifican el estado del sistema como cancelaciones, reagendamientos o procesos de autenticación mediante SMS pienso deben mantenerse bajo supervisión humana o incorporar mecanismos adicionales de verificación antes de ejecutar cambios sobre la base de datos.

La incorporación de RAG mediante la estrategia headers permitió que el agente recuperara únicamente las secciones relevantes de la política y mantuviera el mismo desempeño observado en el baseline, mejorando además la trazabilidad de las decisiones al fundamentarlas explícitamente en las reglas del dominio. Por otro lado, la condición con think no pudo evaluarse completamente debido a las limitaciones experimentales observadas durante la ejecución de las simulaciones, por lo que no fue posible determinar de forma concluyente si esta técnica aporta una mejora cuantitativa en el desempeño del agente. Como trabajo futuro, sería recomendable repetir las simulaciones con una infraestructura que permita completar todas las corridas, además de incorporar mecanismos de planificación, validación automática de flujos y control explícito del estado conversacional para reducir los casos que terminan por MAX_STEPS.

Considerando la criticidad de las operaciones dentro del contexto de salud, se propone utilizar diferentes umbrales mínimos de aceptación según el tipo de tarea. Para consultas informativas, validaciones y recuperación de políticas, un desempeño mínimo de 4/5 (80%) puede considerarse aceptable debido al bajo riesgo asociado. En cambio, para operaciones que modifican información clínica o administrativa como cancelaciones, reagendamientos o validaciones de identidad mediante SMS se recomienda exigir un desempeño de 5/5 (100%), ya que cualquier error puede afectar directamente la atención del paciente y la integridad de la información registrada.
